# Vision Document: StoreLoop

## Executive Summary

StoreLoop는 **본사·지역·OFC가 매장 운영 데이터를 관리하고 대시보드에서 현황과 개선 우선순위를 판단하며, 점주가 AI 피드백으로 현장의 진열을 개선하는 데이터 기반 매대 운영·관제 플랫폼**이다.

본사와 OFC는 매장·담당 관계, 계층별 가이드라인, 우수 매대 Reference, 제출 사진, AI 평가와 조치 이력을 하나의 체계로 관리한다. 관제 대시보드에서는 담당 범위의 제출 현황, 가이드라인 준수 추이, 확인이 필요한 매장과 미해결 건을 파악하고, 개별 매장의 사진·평가 근거·이력까지 확인해 대응 우선순위를 정한다. 축적된 데이터는 지역·매장·카테고리별 운영 비교와 매출 데이터의 상관관계 분석에도 활용한다.

점주의 사진 제출과 AI 진열 컨설팅은 현장 개선을 지원하면서 관제에 필요한 데이터를 축적하는 핵심 접점이다. StoreLoop는 **운영 데이터 관리, 본사·OFC의 데이터 기반 관제, 점주의 현장 개선을 연결하는 통합 매대 운영 플랫폼**을 지향한다.

## Business Context

### Problem Statement

GS리테일과 같은 편의점/유통 가맹 구조에서는 매대 진열 기준(상품 배치, 페이싱, 카테고리 존 구성 등)이 본사 지침, 지역 특성, 매장 특성, 매대(카테고리)별 세부 규칙으로 여러 층위에 걸쳐 존재한다. 점주는 이 기준을 정확히 인지하기 어렵고, 매대 정리 방법이 맞는지 궁금할 때마다 OFC에게 전화나 방문 시 구두로 질문하는 것이 유일한 확인 경로다. 이 방식은 다음과 같은 문제를 발생시킨다.

* 본사·OFC가 매장별 제출 현황, 준수 추이, 미해결 사항을 한 화면에서 비교하기 어려워 관리 우선순위를 정하는 데 시간이 걸린다.
* 매장 정보·담당 관계·가이드라인·Reference·평가 이력이 분산되어 최신 기준과 판단 근거를 일관되게 관리하기 어렵다.
* OFC 1인이 담당하는 매장 수가 많아 응답과 방문이 즉시 이루어지기 어렵다.
* 동일한 가이드라인이라도 OFC 개인의 해석과 경험에 따라 피드백 내용과 기준이 달라진다.
* 점주가 받은 피드백이 기록으로 남지 않아, 이전에 어떤 지적을 받았고 어떻게 개선했는지 추적이 어렵다.
* 매대 준수 여부가 실제 매출에 어떤 영향을 주는지 데이터로 검증되지 않아, 가이드라인의 효과를 정량적으로 설명하기 어렵다.

따라서 본사·지역·매장·매대 단위의 기준과 현장 데이터를 일관되게 관리하고, 대시보드에서 현황을 파악한 뒤 개별 근거를 확인하여 조치로 연결하는 **운영 데이터 관리·관제 체계**가 필요하다. 점주의 사진 기반 AI 컨설팅은 이 체계 안에서 현장의 실행을 돕고, 개선 결과가 다시 관리자 판단과 운영 기준 보완에 반영되도록 한다.
### Business Drivers

* **Data-Driven Control**: 본사·지역·OFC가 담당 범위의 현황·변화·확인 필요 건을 대시보드에서 파악하고 근거를 확인해 대응 우선순위를 결정
* **Operational Data Management**: 매장·담당 관계·가이드라인·Reference·평가·조치 이력을 연결해 등록·조회·수정·변경 이력을 관리
* **Instant Feedback**: OFC의 방문/응답을 기다리지 않고 사진 업로드 즉시 매대 상태에 대한 1차 피드백 제공
* **Standardization**: OFC 개인 경험에 의존하던 매대 판단 기준을 본사/지역/매장/매대 단위의 구조화된 가이드라인으로 표준화
* **OFC Productivity**: OFC가 담당 매장 전체를 직접 순회하지 않아도 AI가 1차 스크리닝을 수행하여 현장 방문의 우선순위를 정할 수 있도록 지원
* **Traceability**: 점주별·매장별 매대 개선 요청과 피드백, 재피드백 이력을 시계열로 축적
* **Data-Driven Merchandising**: 매대 준수도와 매출 데이터의 상관관계를 파악하여 가이드라인의 실효성을 정량적으로 검증
* **AI-assisted Visual Consulting**: Vision AI를 활용해 가이드라인 텍스트 및 Reference 사진과 실제 매대 사진을 비교하고, 우수한 점과 개선할 점을 자동으로 도출

### 역할과 책임의 구분

* **영업 운영(본사·지역·OFC)**: 진열 가이드라인·Reference의 업무 내용, 매장 평가 해석, 현장 조치와 개선 우선순위를 담당한다.
* **플랫폼 운영자(`platform_operator`)**: 계정 활성 상태와 역할·접근 범위, 조직·매장·카테고리 기준 정보, 사용자와 매장 연결, 서비스 처리 상태와 장애 대응을 담당한다. 본사 역할과 구분된 운영 권한을 사용한다.
* **점주**: 자신에게 연결된 매장의 사진·질문 제출과 피드백 확인, 현장 개선을 수행한다.

플랫폼 운영 화면은 영업 관제 화면과 목적·접근 권한을 구분한다. 플랫폼 운영자라는 이유로 모든 매장 사진·매출·평가 본문에 자동 접근하거나 영업 기준·평가 결과를 임의로 수정할 수 있게 하지 않는다. POC의 운영 화면은 계정·연결 정보와 처리 상태·오류 분류 등 운영에 필요한 정보만 제공한다.

## Business Constraints

* 초기 POC는 전체 상품 카테고리를 대상으로 하지 않고, 대표 매대 유형(예: 스낵/음료 등 4~6개 카테고리) 중심으로 검증한다.
* AI 리뷰는 OFC의 현장 판단과 최종 승인을 완전히 대체하지 않는다. **AI는 1차 진단·보조 컨설팅 역할**을 하며, 최종 조치와 예외 판단은 OFC/점주가 수행한다.
* 이미지 비교는 사전 등록된 가이드라인 텍스트 및 우수 매대 Reference 사진을 기준으로 하며, 사전 정보 없이 임의 매대를 완전 자유형으로 인식·평가하는 것을 목표로 하지 않는다.
* 매출 상관관계 분석은 상관관계(correlation) 수준까지만 다루며, 인과관계(causation) 증명이나 매출 예측을 목표로 하지 않는다.
* 매장 사진과 매출 데이터는 민감한 영업 정보이므로, 조회 권한은 담당 OFC → 지역 → 본사 순의 역할 기반 접근 범위로 제한한다.
* 해커톤(오버나이트 루프 엔지니어링) 특성상 실제 매출 연동은 Mock 데이터로 대체한다. 인증/인가는 최소 구성으로 구현하되 플랫폼 운영 권한과 영업 데이터 접근 권한은 구분한다.
* 플랫폼 운영자는 계정을 비활성화하거나 역할·담당 연결을 변경할 수 있으나 변경 이후 접근 권한을 다시 검증해야 한다. 비활성화된 계정은 기존 로그인 상태에서도 보호된 기능에 접근할 수 없어야 한다.
* 사용 중인 조직·매장·카테고리는 연결된 과거 기록을 보존하며 비활성화한다. POC에서는 운영 화면의 영구 삭제를 제공하지 않는다.
* 플랫폼 운영자의 권한·연결 변경과 장애 재처리에는 수행자·대상·시각·사유·결과를 남긴다.

# Full Scope Vision

## Product Vision Statement

**StoreLoop는 본사·OFC의 데이터 기반 관제와 점주의 현장 개선을 연결하고, 매대 운영 데이터와 기준을 일관되게 관리하는 통합 운영 플랫폼이 된다.**

제품은 세 가지 핵심 축을 함께 제공한다.

* **운영 데이터 관리**: 매장과 담당 관계, 가이드라인과 버전, Reference, 사진·평가·개선 이력을 연결해 관리자 판단의 기준을 유지한다.
* **본사·OFC 관제 대시보드**: 전사·지역·담당 매장 범위의 현황과 추이를 비교하고, 확인이 필요한 매장·항목을 찾아 원본 데이터와 평가 근거를 확인한다.
* **점주 현장 개선**: 사진과 질문으로 AI 피드백을 받고 개선 후 다시 제출한다. 이 결과는 관리 데이터로 축적되어 관제와 기준 보완에 활용된다.

데이터 등록과 관리에서 시작해 현황 파악·우선순위 결정·현장 개선·결과 확인으로 이어지는 운영 흐름을 하나의 제품에서 제공한다.

이 세 축을 지속적으로 제공하기 위한 **플랫폼 운영 기반**을 함께 갖춘다. 플랫폼 운영자는 사용자가 올바른 조직·매장 범위로 서비스를 이용하도록 관리하고, 서비스와 AI 분석의 실패를 확인·복구한다. 영업 판단과 서비스 운영 책임을 구분한다.

### Feature Areas

#### Feature Area 1: Store & Access Management

플랫폼 운영자가 점주·OFC·지역·본사 계정의 활성 상태와 역할·접근 범위를 관리하고 조직·매장 연결을 설정한다. OFC의 내 관리 매장 등록은 영업 기능으로 유지하되, 허용된 등록 정책 안에서 수행하고 운영자가 연결 상태를 조회·정정할 수 있다.

**Key Capabilities**

* 매장 등록/조회
* 점주 계정 및 매장 매핑
* OFC 계정 및 "내 관리 매장" 등록
* 지역-매장 계층 구조 관리
* 계정 생성·조회·활성/비활성 및 역할 변경
* 역할 기반 접근 권한 (점주/OFC/지역/본사/플랫폼 운영자)
* 조직·매장 연결 정정 및 변경 이력 조회

#### Feature Area 2: Guideline Management

본사 지침부터 매대 단위 세부 기준까지 계층적 가이드라인을 등록하고 관리한다.

**Key Capabilities**

* 본사 지침 입력
* 지역별 가이드라인 입력

#### Feature Area 8: Platform Operations & Administration

플랫폼 운영자가 서비스 이용 기반과 시스템 처리 상태를 관리한다. 영업 관제 대시보드가 매장 운영과 진열 개선을 다룬다면, 플랫폼 운영 화면은 사용자 접근·기준 정보·서비스 정상 동작을 다룬다.

**Key Capabilities**

* 사용자 계정 생성·검색·활성/비활성, 역할·소속·접근 범위 관리
* 지역·매장·카테고리의 등록·수정·비활성화와 연결 관계 관리
* 계정·매장 매핑 누락 등 이용을 막는 기본 데이터 오류 확인·정정
* API·AI 분석 서비스의 가용 상태, 대기·처리 중·완료·실패 현황 조회
* 실패 작업의 오류 분류·발생 시점 확인과 수동 재처리
* 주요 권한·기준 정보·연결 변경 및 재처리의 운영 이력 조회
* 후속 확장: 운영 공지·점검 안내, 장애 알림, 데이터 보존·백업/복구 정책 관리

재처리는 종료된 실패 작업만 대상으로 한다. 진행 중이거나 이미 성공한 작업을 중복 실행하지 않으며, 기존 실패 기록과 새 처리 시도의 관계를 남긴다. 운영 화면에서 AI 결과를 직접 성공으로 바꾸거나 평가 내용을 덮어쓰지 않는다. 운영 오류에는 인증 정보나 사진·질문 원문을 불필요하게 노출하지 않는다.

# Long-Term Product Flow

**점주(Store Owner) 경로**

→ **매장 선택** → **사진 업로드 & 텍스트 입력** → **전송** → **AI 리뷰 (가이드라인/Reference 비교)** → **검토 결과 보기** → **(필요 시) 재피드백** → **히스토리 기록**

**OFC / 본사 경로**

→ **매장·담당 관계 및 기준 데이터 관리** → **관제 대시보드에서 현황·추이 확인** → **확인 필요 매장·항목 선정** → **사진·평가 근거·이력 조회** → **OFC 대응 및 점주 개선 연결** → **후속 결과 확인** → **기준 보완·분석·리포트**

**플랫폼 운영자 경로**

→ **계정·역할·조직/매장 연결 설정** → **기준 정보와 이용 가능 상태 관리** → **서비스·AI 처리 상태 확인** → **장애 원인 분류 및 실패 건 재처리** → **복구 결과·운영 변경 이력 확인**

점주와 본사·OFC는 공통 운영 데이터를 바탕으로 현장 실행과 영업 관제를 수행한다. 플랫폼 운영자는 별도의 운영 경로에서 접근 권한과 서비스 상태를 관리하여 두 업무 흐름이 지속되도록 지원한다.

# MVP Scope

## MVP Objective

StoreLoop MVP는 대표 매대 카테고리 1~2종에 대해 **운영 기준·데이터 등록 → 점주 사진 제출과 AI 리뷰 → 본사·OFC 대시보드 관제 → 근거·이력 확인 → 현장 개선**의 연결을 검증한다. 점주의 피드백 경험과 관리자의 관제·데이터 관리 경험을 함께 핵심 범위로 둔다.

관리자는 최소 대시보드에서 권한 범위의 제출 현황·확인 필요 건을 확인하고 매장별 평가와 적용 기준을 조회할 수 있어야 한다. 매장·담당 관계, 가이드라인, Reference의 등록·조회·수정과 기본 이력 검색을 우선 완성한다. 상세 추세 비교·상관분석·리포트는 단계적으로 확장하며, 실제 매출 연동은 Mock 데이터로 대체한다.
플랫폼 운영자를 위한 최소 운영 기능도 MVP에 포함한다. 계정·역할·조직/매장 연결과 기본 정보 관리, 서비스·작업 상태 조회, 실패 건 수동 재처리, 주요 운영 변경 이력을 제공한다. 자동 장애 복구·복잡한 권한 승인 체계·백업 정책 관리 화면은 후속 범위다.

# POC Seed / Mock Data Plan

해커톤 기간 동안 실 시스템(본사 상품/재고/POS 등) 연동 없이 End-to-End 데모가 가능하도록, 아래 데이터를 POC 수준의 임시(Mock/Seed) 데이터로 사전에 구성해둔다. 실 데이터가 아니므로 가상의 매장명·인물명으로 구성하고, 시나리오상 그럴듯한 값으로 채운다.

| Data Type | Description | POC 범위 예시 |
|---|---|---|
| 매장 정보 (Store) | 매장명, 지역, 매장 유형(도심형/주택가형 등), 담당 OFC 매핑 | 5~10개 매장 |
| 계정/권한 (Account) | 점주, OFC, 지역 관리자, 본사, 플랫폼 운영자 계정 및 역할 | 각 역할별 1~2개 데모 계정, 운영자와 영업 계정 분리 |
| 가이드라인 (Guideline) | 본사 지침, 지역별/매장별 기준, 매대(카테고리)별 세부 기준 | 스낵/음료 등 1~2개 카테고리 중심, 본사 1~2건 + 지역 2~3건 + 매장/매대 일부 |
| 우수 매대 Reference 사진 | 카테고리별 우수 매대 사진 (가능하면 Before/After 예시 포함) | 카테고리당 2~3장 |
| 재고 (Inventory) | 매장·매대별 상품 재고 수량 | 카테고리당 5~10개 SKU, 매장별 랜덤 수량 |
| 매출 (Sales) | 매장·카테고리별 일별 또는 주별 매출 | 최근 4~8주, 랜덤/시나리오 기반 생성 |
| 제출/리뷰 히스토리 (Submission History) | 데모 초기 화면이 비어 보이지 않도록 사전 적재하는 과거 제출·리뷰 샘플 | 매장당 3~5건 (재피드백 케이스 1건 이상 포함) |
| 플랫폼 운영 시나리오 | 비활성 계정, 연결 누락, 서비스 장애·실패 작업, 운영 변경 내역 | 계정 권한 변경·접근 차단·실패 재처리 사례 각 1건 이상 |

**Mock 데이터 설계 원칙**

* 플랫폼 상태 데모의 장애 fixture는 Mock으로 표시하고 실제 서비스 상태와 구분한다.
* 실제 GS리테일 상호/인물이 아닌 가상 명칭 사용 (예: "OO동점", "XX로점")
* 매출 Mock 데이터는 "가이드라인 준수도가 높을수록 매출이 소폭 상승"하는 패턴을 의도적으로 반영하여, 히스토리·매출 상관계수 데모가 유의미하게 보이도록 생성
* Seed 데이터는 `infra/seed` (또는 `scripts/seed`) 하위 스크립트로 관리하여 언제든 초기화/재실행 가능하도록 구성 (DB 리셋 후 즉시 데모 가능한 상태 복원)
* 매대 사진(우수 Reference 및 리뷰 테스트용)은 저작권 문제가 없는 자체 촬영 사진 또는 공개 이미지로 대체
* Mock 데이터임을 화면 어딘가(예: 관리자 화면 배지, README)에 명시하여 실 데이터로 오인되지 않도록 함

# MVP User Journey

## Journey 1: Store Owner Photo Review Journey

1. 점주가 앱에서 자신의 매장을 선택한다.
2. 매대 사진을 촬영/업로드하고, 궁금한 점을 텍스트로 입력한다.
3. 제출(전송)하면 시스템이 해당 매장·매대에 적용되는 가이드라인과 Reference 사진을 조회한다.
4. AI가 업로드된 사진을 가이드라인 및 Reference와 비교 분석한다.
5. 시스템이 우수한 점과 개선할 점을 포함한 검토 결과를 생성한다.
6. 점주가 검토 결과를 확인한다.
7. 개선이 필요한 경우, 매대를 정리한 뒤 재촬영하여 재피드백을 요청한다.
8. 시스템이 이전 제출과 비교해 개선 여부를 다시 리뷰한다.
9. 모든 제출·리뷰 내역이 히스토리에 기록된다.

**Outcome:** 점주는 OFC의 방문이나 응답을 기다리지 않고, 사진 한 장으로 즉시 매대 개선 방향을 확인하고 스스로 개선할 수 있다.

---

## Journey 2: HQ / OFC Dashboard & Data Management Journey

1. 본사·지역·OFC가 자신의 권한 범위에 해당하는 매장·담당 관계와 가이드라인·Reference를 등록하고 관리한다.
2. 관제 대시보드에서 전사·지역·담당 매장별 제출 현황, 확인 필요 건과 운영 추이를 확인한다.
3. 확인이 필요한 매장이나 항목을 선택해 제출 사진, AI 평가 근거, 적용 기준과 과거 이력을 조회한다.
4. OFC가 현장 확인이나 점주 안내가 필요한 건의 우선순위를 정하고 대응한다.
5. 점주의 후속 제출과 피드백 이력에서 개선 여부를 확인한다.
6. 본사·지역은 반복되는 개선 항목과 우수 사례를 바탕으로 가이드라인·Reference를 보완한다.
7. 축적된 운영 데이터와 매출(Mock)의 상관관계, 기간별 집계를 확인하여 운영 판단을 지원한다.

**Outcome:** 본사·OFC는 관리 데이터를 기준으로 현황을 파악하고, 대시보드에서 발견한 문제를 개별 근거 확인과 현장 개선으로 연결한다. 점주의 후속 결과는 다시 운영 데이터에 쌓여 다음 판단과 기준 보완에 활용된다.

---
## Journey 3: Platform Operator Administration Journey

1. 플랫폼 운영자가 운영 전용 화면에 로그인한다.
2. 신규 계정을 생성하고 역할·지역·매장 연결을 설정하거나 이용 중인 계정의 연결 누락을 정정한다.
3. 지역·매장·카테고리 기준 정보를 관리하고, 사용을 중단하는 항목은 과거 이력을 보존한 채 비활성화한다.
4. 플랫폼 상태 대시보드에서 API·AI 서비스 상태와 처리 지연·실패 작업을 확인한다.
5. 종료된 실패 작업의 오류 분류를 확인하고 원인을 해소한 뒤 수동 재처리를 요청한다.
6. 기존 실패와 재처리 결과를 연결해 확인하고 주요 운영 변경 내역을 조회한다.
7. 이용 중단 계정을 비활성화하고 기존 로그인 상태에서도 보호된 기능에 접근할 수 없는지 확인한다.

**Outcome:** 플랫폼 운영자는 영업 평가 내용을 임의로 바꾸지 않으면서 이용 기반과 서비스 장애를 관리하고, 사용자 접근과 AI 처리 흐름을 정상 상태로 유지한다.

# POC Definition of Done

* 본사·지역·OFC가 역할별 관제 대시보드에서 제출 현황과 확인 필요 건을 조회하고 해당 매장·평가 상세로 이동할 수 있다.
* 매장·담당 관계·가이드라인·Reference를 관리하고, 개별 평가에 적용된 기준과 사진·이력을 확인할 수 있다.
* 데이터가 없는 상태와 AI 판단이 어려운 상태를 정상 준수 상태와 구분해 표시한다.
* 점주가 매장을 선택하고 사진+텍스트를 제출하는 흐름이 End-to-End로 동작한다.
* 매대별/매장별 가이드라인과 우수 매대 Reference 사진을 관리자 화면에서 등록할 수 있다.
* 제출된 사진이 해당 매장·매대에 적용되는 가이드라인/Reference와 비교되어 AI 리뷰 결과가 생성된다.
* 검토 결과 화면에서 우수한 점과 개선할 점을 확인할 수 있다.
* 재피드백(재제출) 후 이전 결과와 비교되는 흐름이 동작한다.
* 점주의 제출/리뷰 히스토리가 기록되고 조회된다.
* OFC가 "내 관리 매장"을 등록하고, 매장별 히스토리를 검색할 수 있다.
* Mock 매출 데이터를 활용한 히스토리-매출 상관계수가 화면에 표시된다.
* 기간별 리포트(기본 집계 화면)를 확인할 수 있다.
* 플랫폼 운영자가 계정·역할·조직/매장 연결을 관리하고, 변경 후 접근 범위와 계정 비활성화가 실제 요청에 반영된다.
* 플랫폼 운영 화면은 일반 영업 계정으로 접근할 수 없으며, 운영자 권한만으로 사진·매출·평가 본문을 조회하거나 수정할 수 없다.
* 운영자가 지역·매장·카테고리를 관리하고 비활성화해도 과거 평가와 연결 이력이 보존된다.
* 플랫폼 상태 화면에서 서비스·작업 실패를 확인하고, 종료된 실패 건을 중복 없이 재처리하여 결과를 확인할 수 있다.
* 주요 권한·기준 정보·연결 변경과 재처리의 대상·수행자·시각·사유·결과를 조회할 수 있다.

| 개인정보/영업정보 노출 | Low | High | 역할 기반 접근 제어 최소 구현, 실 데이터 대신 샘플 데이터 사용 |
| 플랫폼 권한과 영업 권한의 혼동 | Medium | High | 운영 역할과 데이터 접근 권한 분리, 운영 변경 이력과 역할별 접근 검증 |
| 잘못된 연결 변경·비활성화 | Medium | High | 영향 대상 확인, 과거 기록 보존, 변경 사유·이력 관리 |
| 장애 재처리의 중복 실행 | Medium | Medium | 종료된 실패 건만 재처리, 중복 요청 방지 및 처리 시도 연결 |

## Open Questions

* AI 리뷰에 사용할 Vision 모델/API는 무엇으로 할 것인가? (Claude Vision 등 멀티모달 모델 활용 가정)
* 가이드라인 텍스트와 Reference 사진 중 어느 쪽에 더 높은 판단 가중치를 둘 것인가?
* "재피드백"은 완전히 새로운 제출로 취급할 것인가, 기존 제출에 연결된 스레드로 취급할 것인가?
* 매대(카테고리) 분류 체계는 몇 종으로 시작할 것인가? (해커톤 데모 범위)
* OFC의 "내 관리 매장" 등록은 자율 등록인지, 본사가 매핑을 승인/할당하는 구조인지?
* 매출 데이터는 어떤 형태의 Mock으로 생성할 것인가? (일별/주별, 카테고리별 매출)
* AI 판단 결과에 대해 OFC가 직접 수정/오버라이드할 수 있는 기능이 MVP에 필요한가?
* 플랫폼 운영 계정의 최초 발급과 운영자 권한 추가 부여는 누가 책임지는가? POC는 사전 생성한 운영자 계정을 사용하고 운영자 승격 UI는 제공하지 않는다.
* 정식 운영의 장애 지원에 사진·평가 본문 열람이 필요하다면 어떤 별도 승인·접근 이력을 요구할 것인가? POC에서는 해당 본문 열람을 운영자 기본 권한에 포함하지 않는다.
* 운영 공지, 장애 알림, 데이터 보존·백업 정책 관리의 후속 우선순위는 무엇인가?

## Product Vision

**StoreLoop는 본사·OFC의 데이터 기반 관제와 점주의 현장 개선을 연결하는 통합 매대 운영 플랫폼이다.**

운영 기준과 현장 데이터를 일관되게 관리하고, 대시보드에서 현황과 우선순위를 판단하며, AI 피드백과 OFC 대응을 통해 매장 개선으로 이어지게 한다. 개선 결과는 다시 데이터로 축적되어 다음 운영 판단과 기준 보완의 근거가 된다. 플랫폼 운영자는 계정·접근 범위·기준 정보와 서비스 상태를 관리하여 이 흐름이 안정적으로 지속되도록 한다.

> **운영 데이터를 관리하고 → 대시보드로 현황을 파악하고 → 근거로 우선순위를 정하고 → 현장을 개선하고 → 결과를 확인해 기준을 발전시킨다.**

**StoreLoop — 데이터를 관리하고, 매장을 관제하고, 현장을 개선하다.**
