## 1. 제품 범위와 완료 해석

StoreLoop는 기준·Reference 관리 → 점주 사진/질문 → 실제 AI 평가 → 영업 관제·근거 확인 → OFC 조치 → 개선 후 재제출을 연결한다. 플랫폼 운영은 계정·연결·기준 정보·기술 처리 복구를 담당하며 영업 평가와 분리한다.

한 공통 FastAPI·PostgreSQL·독립 worker·로컬 Codex AI 서버와 다섯 React/Vite 패키지를 제공한다. 각 패키지의 단일 빌드에 점주·OFC·지역·본사·운영자 화면을 모두 포함한다. 시안별 업무 규칙과 권한은 동일하다. 구현, 실제 실행, 독립 기능 검증, 독립 디자인 검수, 시연 데이터 및 매뉴얼 인계까지 완료해야 한다. 문서 확정은 G2 시작 조건이다.

00의 MVP 우선순위에서 Should로 분류된 재피드백·상위 기준·기본 분석은 00의 POC DoD, 01 인수 조건 및 사용자 목표에도 필요하므로 이번 **인수 Must**로 계획한다. 이는 필수 기능 추가의 임의 추정이나 상위 문서 수정이 아니라 전체 완료 조건의 교집합을 구현하는 결정이다. 나머지 Should도 Must 후 구현·검증하며 미구현 항목은 명시한다.

## 4. Should

| 요구 ID | 범위 | 수용 기준·검증 |
|---|---|---|
| R-S01 | 운영 공지·점검 안내 | 운영자가 제목·안내·게시 기간·활성 상태를 관리하고 로그인 후 역할별 공통 안내에서 유효 공지 조회. 사유/감사 기록. 개인정보·영업 본문 미포함. `AT-S01` |
| R-S02 | 목록 탐색 편의 | 페이지·필터를 URL에 보존하고 상세 후 돌아갈 때 유지; 목록 재조회 시 기존 내용 위 갱신 표시; 최신 결과 도착은 화면 초점 강제 이동 없이 알림. `AT-S02` |

Should는 Must를 대체하지 않는다. Must 후 구현하며 실제 불채택은 근거·영향·확인 결과를 남긴다. 단순 품질 편의라도 공통의 필수 키보드/오류 안내를 Should로 낮추지 않는다.

## 5. 제외 범위

- 실 매출 시스템 연동, 매출 인과관계 증명·예측, 정식 리포트 export/스케줄링.
- 정교한 segmentation/객체 탐지, 다단계 가이드라인 자동 충돌 해결, 대량 매장 batch 리뷰.
- 실시간 외부 알림·자동 OFC 통지·SMS·이메일·푸시, 자동 장애 복구, 운영 백업/보존 정책 관리 화면.
- SSO·다단계 권한 승인·복수 역할·운영자 승격 UI, 운영자 영업 본문 지원 열람.
- 외부 공개/배포, 유료 자원 구매, 무관한 리팩터링, 사용자 데이터 삭제, 자동 최종 시안 선택.
- 개발 세션 시간·에이전트 수 계측 기능. 서비스 처리 지연·감사 기록은 필수 범위다.

## 6. 상태·데이터 표현 수용 규칙

| 의미 | 사용자 표현 | 업무상 처리 |
|---|---|---|
| 미제출 | “선택한 기간에 제출한 사진이 없습니다” | 0점·미준수로 집계하지 않음 |
| queued / running | “분석 대기 중” / “사진을 분석하고 있어요” | 업로드와 분석 단계를 분리; 재제출 버튼 중복 방지 |
| succeeded + unknown | “사진만으로 판단하기 어려워요” | 정상 결과의 제한 사항·재촬영·OFC 확인으로 연결 |
| failed | “분석을 완료하지 못했어요” | 안전한 오류 분류, 재조회/운영 문의; 실패를 평가 0점으로 바꾸지 않음 |
| 기준 없음 | “적용할 기준이 없어 OFC 확인이 필요해요” | 임의 규칙 생성 금지, 판단 가능률/준수율 계산 한계 |
| Reference 없음 | “비교 Reference가 없습니다” | 없는 사진을 비교했다고 표시하지 않음 |
| Mock / 생성 이미지 | “Mock 데이터” / “AI 생성 시연 이미지” | 결과·차트·매뉴얼에 맥락 유지; 실제 분석 출처와 별도 표기 |
| 계산 불가 | “표본 부족” / “값의 변화가 없어 계산할 수 없습니다” | null을 0 또는 정상 수치로 표시하지 않음 |

성공 평가의 준수율은 판단 가능한 pass+fail 기준 중 pass 비율이며, 판단 가능률은 전체 적용 기준 중 pass+fail 비율이다. 분모 0은 `—`와 이유를 표시한다. 실제 계산 필드와 rounding은 AI/API 계약을 따른다.

## 7. 디자인·매뉴얼·인계 완료 증거

각 시안의 `brief.md`, `design-spec.md`, `acceptance.md` 버전을 프론트가 적용하고 독립 디자인 검수자는 `execute/designReview/concept-0N/`에 화면 증거와 기준별 결과를 남긴다. 04 공통 화면/상태 기준과 각 시안의 구체 배치 기준을 함께 통과해야 한다.

`deliverables/manuals/concept-0N/index.html`은 완성된 해당 시안의 실제 화면으로 작성한다. 컨셉·한 접속 주소·실행 전제·5개 역할 동선·점주 전체 흐름·기준/Reference·관제/이슈/분석·운영 재처리/권한·오류/unknown·Mock/생성 이미지·알려진 제약·처음부터 끝까지 시연 순서·화면 캡처를 담는다. UTF-8, 내부 목차/링크, 상대 경로 이미지, 외부 CDN 없이 열람, 비밀 없는 내용이 필수다. 로그인 비밀번호는 런타임 로컬 자격 안내 위치만 설명하며 문서에 고정하지 않는다.

최종 사용 시안 선택은 사람이 한다. 5개 기술 구현·검증·인계 완료와 최종 선택 대기를 분리하며 선택 전 소스를 보존한다.

## 8. 공통 계약 확정 조건

03/04 및 DB/API/AI/처리/데이터/검증/실행 계약이 존재하고, API 필드·상태·역할 범위·수용 테스트 ID 간 모순을 독립 검토로 해소해야 한다. 조정자는 확정 버전·결정 근거·검토 결과·담당자 수신 확인을 기록하고 G1을 닫는다. 이 문서 작성자가 검토 없이 확정을 선언하지 않는다.

### PD-003 / WEB01-004 역할 경계 명확화 (2026-09-21)

조정자 독립 정적 검토에 따라 앱 내부 업무 알림은 점주·영업 역할에 한정한다. 운영자에게 영업 알림이 없다는 기존 역할 분리를 메뉴·라우트에도 명시했다. 공지 Should는 모든 역할에서 유지된다. 상위 요구 축소나 API 변경은 아니다. 구현 회귀 검증과 전파는 frontend-concept-01/implementation 이력 참조.
