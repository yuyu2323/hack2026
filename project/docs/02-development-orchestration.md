# 02. 개발 오케스트레이션 및 에이전트 실행 규칙

## 1. 목적과 적용 시점

StoreLoop를 **하나의 공통 Python 백엔드, 로컬 LLM 처리 서버와 서로 다른 컨셉의 React 프론트엔드 5개 시안**으로 구현한다. 전체 작업은 오케스트레이션 에이전트가 관리하며, 독립 서브에이전트가 도메인 개발·시안별 기획과 디자인·시안 개발·통합 테스트·최종 디자인 검수·데이터·이미지·사용자 매뉴얼을 담당한다. 최종 사용할 컨셉은 최종 구현 후 사람이 선택한다.

이 문서는 문서 준비부터 구현·검증·시연 인계까지 이어지는 실행 계약이다. 사람이 **“작업 시작”을 지시하면 각 서비스 구현에 필요한 후속 문서의 조사·작성·보완부터 자동으로 수행하고, 필요한 공통 문서의 작성과 내부 검토가 끝나면 추가 승인이나 별도의 “구현 시작” 지시를 기다리지 않고 구현에 착수한다.** 작업 시작 지시는 이 전체 흐름을 수행하라는 지시로 해석한다. 단, 지금처럼 특정 문서의 작성·수정만 요청받은 경우에는 해당 문서 작업만 수행한다.

- **MUST / 필수**: 완료 판정에 반드시 충족해야 한다.
- **MUST NOT / 금지**: 에이전트가 자의적으로 수행하지 않는다.
- **SHOULD / 권장**: 다른 방식을 선택하면 이유와 검증 결과를 작업 이력에 남긴다.
- 이 문서의 `/execute/...`는 운영체제 루트가 아닌 **현재 project 루트 기준 상대 경로**다.
- `checkList`, `workHitory`, `question`은 지정된 실제 폴더 이름이다. `workHitory`를 `workHistory` 등으로 바꾸지 않는다.

## 2. 강제 문서와 변경 재량

| 문서 | 적용 규칙 |
|---|---|
| `docs/00-vision.md` | 제품 목적, 사용자, 업무 범위, 권한·데이터 원칙을 강제한다. |
| `docs/01-architecture.md` | React/Python 스택, 컨셉별 패키지·역할별 화면 모듈, 단일 업무 백엔드, 로컬 AI 서버, 처리·권한 구조를 강제한다. |
| `docs/02-development-orchestration.md` | 본 문서. 작업 분담, TDD, 기록, 검증, 시안 선택 절차를 강제한다. |
| 그 외 후속 문서 및 기존 작업 패키지 | 기본 입력으로 읽되 구현에 꼭 필요한 경우 에이전트가 수정할 수 있다. |

1. 에이전트는 00 → 01 → 02 → 담당 작업에 필요한 후속 문서 순서로 읽는다. 존재하지 않는 문서는 확정된 계약으로 취급하지 않는다.
2. 00·01·02는 사람의 명시적 변경 지시 없이 수정하거나 우회하지 않는다. 문서 사이의 실제 충돌은 해당 부분을 질문으로 남기고 영향을 받지 않는 작업을 계속한다.
3. 후속 문서 변경은 00·01·02와 호환되어야 한다. 테스트 실패를 숨기거나 필수 기능을 제거하기 위해 요구사항을 낮추지 않는다.
4. 후속 문서는 변경 이유·변경 전후·영향 모듈·호환성·검증 계획을 먼저 작업 이력에 기록하고 수정한다. 완료 후 실제 검증 결과와 변경 파일을 추가한다.
5. API·DB·공유 타입 변경은 오케스트레이터와 해당 소유자에게 공유하고, 계약을 먼저 갱신한 뒤 구현한다. 영향을 받는 5개 시안과 테스트·매뉴얼도 함께 갱신한다.
6. `00`의 미결 질문 중 `01`에서 이미 결정한 기술 사항은 재질문하지 않는다. 예를 들어 기본 AI 실행 연결은 `01`의 Codex 어댑터를 따른다.

후속 문서 변경 이력은 `execute/workHitory/{module-id}/{task-id}.md`에 남긴다. 여러 모듈에 걸친 문서 변경은 `docs` 모듈 이력에 원본을 작성하고 관련 모듈에서 링크한다.

### 2.1 후속 MD 변경의 담당 에이전트 전파 — 필수

후속 MD 파일을 수정한 에이전트는 **수정된 부분을 담당하거나 그 내용을 사용하는 모든 영향 대상 에이전트와 오케스트레이터에게 변경 사항을 전파해야 한다.** 파일 저장이나 변경 이력 작성만으로 전파 완료로 간주하지 않는다. API·DB뿐 아니라 화면, 업무 규칙, AI 평가, 테스트, 시드·이미지, 실행 절차, 매뉴얼 등 모든 후속 MD에 적용한다.

1. **영향 식별**: 변경한 절·요구사항과 작업 배정표를 대조하여 영향 모듈·담당 에이전트·진행 중 작업을 식별한다. 공통 계약 변경은 해당 계약을 사용하는 프론트 시안·백엔드·AI·테스트·데이터·매뉴얼 담당까지 확인한다.
2. **변경 전달**: 저장한 변경을 에이전트 간 메시지로 즉시 알린다. 문서 경로·절, 변경 식별자, 변경 전후 요약, 이유, 적용 대상, 필요한 후속 행동, 변경 이력 링크를 포함한다. 변경 식별자는 커밋 ID 또는 문서 변경 번호 등으로 두어 어느 내용을 전달했는지 구별한다.
3. **수신 확인**: 각 담당 에이전트는 변경된 부분을 다시 읽고, 확인한 변경 식별자와 자기 작업의 영향·반영 계획을 자신의 작업 이력에 기록한 뒤 발신자와 오케스트레이터에게 알린다. 기존 가정이 무효가 되면 관련 체크리스트와 수용 기준부터 갱신한다.
4. **반영·재검증**: 담당자는 필요한 문서·소스·테스트·데이터·매뉴얼을 수정하고 결과를 회신한다. 영향이 없다고 판단한 경우에도 근거를 기록한다. 구버전 계약과 충돌하는 작업만 보류·재조정하며 무관한 작업은 계속한다.
5. **전파 추적**: 오케스트레이터는 변경 이력에 대상별 `전달 대기 → 전달 완료 → 확인 완료 → 반영·검증 완료` 상태와 근거 링크를 관리한다. 관련 대상의 반영·검증 또는 영향 없음 확인이 끝나야 변경 건을 완료 처리한다. 수신 확인을 사람의 추가 승인 절차로 바꾸지 않는다.
6. **부재·교체 대응**: 담당자가 미배정·종료·중단 상태이면 전달 대기로 기록하고 오케스트레이터가 담당자를 배정하거나 재개시킨다. 새 담당자는 관련 작업을 시작하기 전에 미반영 변경을 읽고 확인한다. 무응답을 확인 완료로 처리하지 않는다.

변경 원본 이력에 다음 표를 추가하고, 각 담당자의 작업 이력에는 해당 변경 링크를 남긴다. 표의 수정 소유자는 오케스트레이터 한 명으로 정해 동시 수정 충돌을 방지한다.

| 변경 식별자 / 문서·절 | 영향 모듈 / 담당 에이전트 | 필요한 후속 행동 | 전파 상태 | 확인·반영·검증 근거 링크 |
|---|---|---|---|---|
| {change-id / 경로·절} | {module-id / 담당자} | {수정 또는 재검증 항목} | 전달 대기 | {담당 작업 이력 링크} |

## 3. 결과물의 단위와 소스 구조

### 3.1 하나의 백엔드와 5개의 완전한 시안

**시안 1개 = web-concepts-0N이라는 하나의 React 패키지 안에 점주·영업 관리자·플랫폼 운영자 화면을 모두 포함한 프론트엔드**다. 영업 관리자 영역은 OFC·지역·본사의 역할별 범위를 지원한다. 5개 시안은 같은 역할과 업무 흐름을 제공하며, `01`에 따라 소스 모듈·메뉴·라우팅·서버 권한을 역할별로 분리한다. 역할별로 별도 패키지를 빌드하거나 서버를 실행하지 않는다.

- 5개 시안 모두 하나의 FastAPI 업무 API, 같은 DB 스키마, 같은 인증·권한 규칙, 같은 로컬 AI 서버를 사용한다.
- 백엔드를 시안별로 복제하거나 컨셉 번호에 따라 권한·점수·업무 규칙을 바꾸지 않는다.
- 각 시안은 독립된 React 소스와 하나의 빌드·실행 진입점을 갖는다. 스크린샷이나 정적인 목업만으로 완료할 수 없다.
- 차별화는 정보 구조, 화면 배치, 탐색 방식, 데이터 표현, 작업 동선에서 만든다. 색상만 바꾼 5개 테마로 대체하지 않는다.
- API 클라이언트·타입·검증·접근 가능한 기본 컴포넌트는 공유할 수 있다. 각 시안의 화면 구성과 스타일은 독립적으로 수정할 수 있어야 한다.
- 모든 시안은 동일한 기능 체크리스트를 충족한다. 특정 컨셉을 강조한다는 이유로 다른 필수 기능을 생략하지 않는다.

### 3.2 구현 단계의 디렉터리 규약

아래는 생성할 구조이며, 문서 작성만으로 실제 폴더와 파일을 생성할 필요는 없다. project 바로 아래에 web-concepts-01부터 web-concepts-05까지 배치한다. 각 컨셉 패키지 내부에서 역할별 화면 소스를 분리한다.

```text
project/
├─ docs/
│  ├─ 00-vision.md
│  ├─ 01-architecture.md
│  └─ 02-development-orchestration.md
├─ web-concepts-01/             # 컨셉별 하나의 React/Vite 패키지
│  ├─ package.json             # dev / build / preview
│  ├─ src/
│  │  ├─ app/                  # 공통 진입점·로그인·역할별 라우팅
│  │  ├─ store-owner/          # 점주 화면
│  │  ├─ ofc-admin/            # OFC·지역·본사 화면
│  │  ├─ platform-admin/       # 플랫폼 운영 화면
│  │  └─ shared/              # 해당 컨셉의 공통 UI
│  └─ dist/                   # 한 번의 빌드로 생성하는 전체 프론트
├─ web-concepts-02/             # 01과 동일한 패키지 구조
├─ web-concepts-03/
├─ web-concepts-04/
├─ web-concepts-05/
├─ packages/
│  └─ api-client/              # 컨셉 간 공통 API 타입·세션/CSRF 처리
├─ server/                          # 단 하나의 FastAPI 업무 백엔드
├─ ai-service/                      # 필수 Python 로컬 AI 서버
├─ scripts/seed/                    # 재실행 가능한 시드와 이미지 manifest
│  └─ assets/shelves/               # 생성한 시연용 매대 이미지
├─ deliverables/manuals/
│  ├─ concept-01/index.html         # 역할별 안내를 포함한 시안별 매뉴얼
│  └─ ... concept-05/index.html
└─ execute/
   ├─ checkList/{module-id}/{task-id}.md
   ├─ workHitory/{module-id}/{task-id}.md
   ├─ question/{module-id}/{question-id}.md
   ├─ design/concept-01/ ... concept-05/       # 시안별 기획·디자인 명세와 참고 자료
   └─ designReview/concept-01/ ... concept-05/ # 독립 디자인 검수 보고서·화면 증거
```

실행 명령·포트·환경 설정은 오케스트레이터가 작업 이력에 실행표로 관리한다. `01`의 기본 포트는 대표 실행 구성에 사용하고 나머지 시안에는 충돌하지 않는 포트를 배정한다. 모든 시안을 동시에 실행할 필요는 없지만 각각 재현 가능한 실행·빌드 명령이 있어야 한다. 개발 시 origin·CSRF 설정은 실제 사용하는 주소만 허용한다.

### 3.3 컨셉 패키지의 빌드·실행 계약

의존성 설치와 환경 설정 후 각 `web-concepts-0N` 디렉터리에서 다음 명령을 사용할 수 있도록 구현한다. 아래는 구현 시 제공해야 할 명령 계약이며 현재 문서 수정 단계에서 실행하지 않는다.

```sh
npm run dev      # 해당 컨셉의 전체 프론트 개발 서버 하나 실행
npm run build    # 모든 역할의 화면을 포함한 dist를 한 번에 생성
npm run preview  # 생성된 dist를 서버 하나로 확인
```

- 각 컨셉은 자신의 package.json과 Vite 설정을 갖는다. 다른 컨셉이나 역할별 하위 폴더에서 추가 빌드를 요구하지 않는다.
- 공통 packages/api-client는 각 컨셉의 빌드 과정에서 함께 처리한다. 의존성 설치 방식과 재현 가능한 lockfile 관리는 공통 실행 문서에 정한다.
- 로그인 후 역할에 따라 /store-owner, /ofc-admin, /platform-admin으로 이동한다. 하나의 호스트에서 역할별 경로를 제공하고 직접 URL 접근·새로고침도 지원한다.
- 모든 역할 화면이 같은 산출물에 포함되어도 데이터 권한은 FastAPI에서 검증한다. 컨셉 또는 역할 선택 UI로 다른 역할의 권한을 얻을 수 없어야 한다.
- 빌드는 정적 프론트 산출물을 만드는 과정이다. 실제 기능을 보려면 공통 백엔드·작업자·AI 서버를 실행하고 preview 또는 정적 서버로 접속한다. 정적 서버에는 SPA 경로 fallback을 설정한다.
- 통합 테스트 담당자는 각 컨셉의 단일 빌드 산출물에서 5개 역할의 화면과 핵심 흐름을 검증한다. HTML 매뉴얼에는 컨셉당 하나의 접속 주소와 역할별 이용 방법을 안내한다.

## 4. 에이전트 역할과 파일 소유권

| 역할 / module-id 예시 | 책임 | 필수 산출물 |
|---|---|---|
| 오케스트레이터 / `orchestration` | 작업 분해, 의존성·담당자·수정 경로 배정, 통합, 완료 판정 | 전체 체크리스트, 배정표, 현황, 실행표, 최종 인계 |
| DB 스키마 전문가 / `db-schema` | 초기 관계·제약·인덱스·마이그레이션 설계, 이후 스키마 변경 통합 | ERD, 데이터 사전, 제약 및 마이그레이션 순서, 검증 결과 |
| 도메인 개발 / `backend-{domain}` | 담당 FastAPI 모듈의 계약·TDD·구현 | 소스, 테스트, 계약 변경 이력 |
| 로컬 AI 개발 / `local-ai` | 실제 이미지·질문·기준·Reference 분석 서버와 실행 어댑터 | 구조화 결과, 입력 검증, 실제 분석 및 장애 테스트 |
| 기획·디자인 / `design-concept-01` … `05` | 각 시안의 사용자 경험·컨셉·룩앤필·톤앤매너 및 검수 기준 정의 | execute/design 아래 시안별 기획서·디자인 명세·검수 기준 |
| 최종 디자인 검수 / `design-review-concept-01` … `05` | 해당 시안의 기획·디자인·개발 담당자와 독립적으로 실제 화면의 명세 준수 확인 | execute/designReview 아래 불일치·화면 증거·수정 재검수 보고서 |
| 프론트 개발 / `frontend-concept-01` … `05` | 한 컨셉 패키지의 역할별 화면 구현과 API 연결 | React 소스, 컴포넌트 테스트, 빌드, 시안 설명 |
| 통합 테스트 / `integration-concept-01` … `05` | 개발 담당자와 독립적으로 해당 시안의 전체 흐름 검증 | Playwright 테스트, 결과·결함·재검증 보고서 |
| 시드 데이터 / `demo-data` | 현실적인 가상 데이터 및 관계 구성, 초기·최종 적재 | 재실행 가능한 시드, 데이터 목록, 정합성 검증 |
| 매대 이미지 생성 / `demo-images` | Reference·제출·개선 전후·판단 곤란 사진 생성과 확인 | 실제 이미지 파일, manifest, 시나리오 연결 |
| 매뉴얼 / `manual-concept-01` … `05` | 완성된 시안별 기능·역할·시연 안내 작성 | 각 시안의 HTML User Manual |

### 병렬 작업 규칙

1. 오케스트레이터는 작업 시작 지시를 받으면 문서 준비 단계부터 독립 서브에이전트를 실제 배정한다. 자신이 모든 역할을 수행한 뒤 역할명만 나눠 기록하지 않는다.
2. 가용 동시 실행 수에 맞춰 순차 배치한다. 5개 시안 에이전트를 한 번에 실행할 수 없어도 전체 5개를 각각 담당하게 한다.
3. 하나의 파일에는 동시에 하나의 수정 소유자만 둔다. 공유 API 타입, 루트 설정, 공통 UI, DB 마이그레이션은 소유자를 명시한다.
4. 다른 모듈 파일 변경이 필요하면 변경 제안을 기록하고 소유자·오케스트레이터에게 전달한다. 공유 파일을 무단으로 함께 수정하지 않는다.
5. 작업은 입력·출력·완료 조건이 명확한 크기로 나누고 독립 작업마다 서브에이전트를 배정한다. 의미 없는 반복 작업이나 대기만으로 실행을 늘리지 않는다.
6. Must 완료 후에는 Should, 독립 검토, 발견된 결함 수정, 데이터·사용성·시연 품질 개선을 이어간다. 개발 세션 시간이나 에이전트 생성 수를 계측·집계하는 기능은 만들지 않는다.
7. 작업자 교체·중단·컨텍스트 인계 시 다음 담당자가 체크리스트와 이력만으로 이어갈 수 있도록 현재 상태와 다음 행동을 남긴다.

## 5. 작업 시작·공유·질문 프로토콜

### 5.0 작업 시작 지시를 받은 오케스트레이터의 자동 실행

1. 00·01·02와 기존 후속 문서를 읽고, 공통 백엔드·로컬 AI 서버·5개 프론트 시안 구현에 필요한 문서를 식별한다. 먼저 자신의 체크리스트를 작성하고 문서별 담당자와 수정 경로를 배정한다.
2. 기존 문서는 재사용·보완하고 없는 문서는 담당 에이전트가 작성한다. 문서가 없다는 이유만으로 사람이 내용을 채워 주기를 기다리지 않는다. 각 문서 담당자도 작성 전에 체크리스트를 남긴다.
3. 아래 공통 문서를 구현에 필요한 수준으로 완성한다. 파일명·문서 분할은 기존 구조에 맞게 정하고, 오케스트레이터의 체크리스트에 실제 경로와 상태를 기록한다.
4. 오케스트레이터와 관련 담당자가 문서 사이의 이름·타입·권한·상태 전이·소유권을 대조한다. 00·01·02와의 정합성 및 공통 문서 완료 조건을 확인하고 결과를 작업 이력에 남긴다. 이 검토는 에이전트의 내부 검토이며 사람의 일괄 승인을 요구하지 않는다.
5. 공통 문서 준비가 끝나면 즉시 구현 작업을 배정하고 TDD를 시작한다. 문서 작성 완료 보고만 남기고 작업을 종료하거나 “구현을 시작할까요?”라고 묻지 않는다.
6. 구현 중 발견한 세부사항은 해당 서비스 문서에 먼저 보완한 뒤 구현한다. 다른 모듈에 영향을 주는 변경은 계약 소유자와 조정하고 관련 문서·구현·테스트를 함께 갱신한다.

| 공통 문서 영역 | 구현 전 준비할 내용 |
|---|---|
| 서비스·도메인 및 작업 분담 | 공통 백엔드·AI 서버·역할별 화면의 책임, 모듈 경계, 파일 소유권, 작업 패키지와 의존 순서 |
| DB 스키마 | DB 전문가의 초기 엔티티·관계·제약·인덱스·비활성화 정책과 마이그레이션 순서 |
| 공통 API·인증·권한 | 요청·응답·오류·파일 업로드 계약, 세션/CSRF, 역할별 데이터 범위, 상태 전이 |
| 로컬 AI 분석 계약 | 실제 이미지·질문·가이드라인·Reference 입력, 결과 JSON, 실패·타임아웃·재처리와 작업자 연계 |
| 화면·기능 및 시안 기준 | 역할별 업무 흐름, 5개 시안의 동일 기능 범위, 각 컨셉의 차별화 기준과 공통 API 연결 |
| 테스트·시연·실행 계획 | 모듈별 수용 기준, 통합 테스트 시나리오, 시드·이미지 연결 계획, 환경·실행·격리 규칙 |

**공통 문서 완료 조건**은 위 영역의 실제 문서가 존재하고, 담당자·소유권이 정해져 있으며, 서비스 간 연결에 필요한 계약과 수용 기준에 구현을 막는 누락·충돌이 없는 상태다. 파일이나 목차만 만든 상태는 완료가 아니다. 모든 세부 화면 설명이나 최종 사용자 매뉴얼까지 미리 완성할 필요는 없다. 서비스별 세부 설계는 해당 모듈 구현 전에 보완하고, 최종 HTML 매뉴얼은 완성된 화면을 기준으로 작성한다.

사람에게 반드시 물어야 하는 강제 문서의 충돌이나 사업적 판단만 §5.4의 질문 절차로 처리한다. 질문과 관계없는 문서 작업·구현은 계속 진행한다. 공통 문서가 이미 조건을 충족한다면 중복 작성 없이 확인 결과를 기록하고 구현으로 넘어간다.

### 5.1 모든 에이전트의 시작 절차

오케스트레이터, 기획·디자인, 최종 디자인 검수, 통합 테스트, 데이터, 이미지, 매뉴얼 담당을 포함한 **모든 에이전트**에 적용한다.

1. 강제 문서, 담당 계약, 기존 작업 이력, 미해결 질문을 읽는다.
2. `execute/checkList/{module-id}/{task-id}.md`를 먼저 작성한다. 준비를 위한 읽기는 허용하지만 소스·데이터·산출물 작업은 체크리스트 작성 후 시작한다.
3. 선행 작업의 결과와 수정 가능한 경로를 확인하고 오케스트레이터 배정표에 등록한다.
4. 담당 서비스의 필수 문서가 없거나 부족하면 먼저 작성·보완한다. §5.0의 공통 문서 준비와 담당 모듈의 선행 조건이 충족되면 추가 지시 없이 실패하는 테스트부터 구현을 시작한다. 비코드 작업이면 검증 가능한 수용 기준부터 확정한다.
5. 의미 있는 변경·실패·결정·인계 시 작업 이력을 갱신하고 체크리스트 상태를 맞춘다.
6. 자기 검증을 완료하면 `REVIEW`로 전환한다. 필요한 독립 검증과 통합을 통과한 뒤 오케스트레이터가 `DONE`으로 판정한다.

상태는 `TODO → RUNNING → REVIEW → DONE`을 사용한다. 진행 불가능한 선행 조건은 `BLOCKED`, 검토에서 결함이 발견되면 `RUNNING`으로 되돌린다. 실패·미실행·외부 의존성 차단은 성공으로 표시하지 않는다.

### 5.2 체크리스트 템플릿

```markdown
# {task-id}: {작업명}
- 모듈 / 담당 에이전트:
- 상태: TODO
- 목표 / 완료 조건:
- 입력 문서 및 계약 버전:
- 선행 작업 및 결과 링크:
- 수정 가능 경로 / 공유 파일 소유자:
- 작업 이력 / 관련 질문 링크:

## 실행 항목
- [ ] 요구사항과 수용 기준 확인
- [ ] 실패 테스트 확인 또는 비코드 검증 기준 정의
- [ ] 구현 또는 산출물 작성
- [ ] 성공 테스트 및 회귀 검증
- [ ] 권한·오류·빈 상태 등 해당 경계 검증
- [ ] 필요한 후속 문서 변경 및 이력 작성
- [ ] 후속 MD 변경을 영향 대상 담당자에게 전파하고 확인·반영·검증 추적 (§2.1)
- [ ] 독립 검증 요청 및 인계
```

### 5.3 작업 이력 템플릿

```markdown
# {task-id}: {작업명}
- 담당 / 체크리스트 링크:
- 현재 상태 / 검증한 소스 버전 또는 파일 상태:

## 작업 기록 — 새 기록을 아래에 추가
- 수행 작업과 변경 파일:
- 결정 및 근거:
- 테스트 명령 / 기대 결과 / 실제 결과:
- TDD 증거: RED 실패 이유 → GREEN 통과 → REFACTOR 재검증
- 계약·문서 변경: 변경 전후 / 이유 / 영향 / 검증 결과
- 변경 전파: 변경 식별자 / 수신 대상 / 확인 상태 / 반영·검증 근거 링크
- 발견한 문제 / 의존 모듈에 전달할 내용:
- 다음 작업 / 재현 방법 / 산출물 링크:
```

각 에이전트는 자기 task 파일에 기록을 추가하며 다른 에이전트의 이력을 덮어쓰지 않는다. 최신 현황은 오케스트레이터의 체크리스트에서 원본 이력으로 링크한다. 대화 메시지만을 인계 수단으로 사용하지 않는다. 인증 값·개인정보·사진 원문 등 불필요한 민감 정보는 이력에 복사하지 않는다.

### 5.4 인간 판단 질문 템플릿

질문은 **사람의 판단 없이는 결정할 수 없는 사안**에만 작성한다. 이미 문서에 정해진 사항이나 에이전트가 선택할 수 있는 구현 세부사항은 질문 대신 근거를 기록하고 진행한다.

```markdown
# {question-id}: {결정할 사안}
- 상태: OPEN
- 작성 모듈 / 관련 작업:
- 질문이 필요한 이유:
- 결정에 필요한 근거·화면·비교 자료 링크:
- 답변이 없을 때 보류할 작업:
- 답변과 무관하게 진행할 작업:

## 선택지
- [ ] A. {선택안} — 장점 / 비용·제약
- [ ] B. {선택안} — 장점 / 비용·제약
- [ ] C. {필요한 경우 추가 선택안} — 장점 / 비용·제약

## 사람의 답변
- 선택: 미응답
- 보충 의견:
- 답변자 / 답변 근거:

## 반영 결과
- 반영 작업 / 검증 결과:
```

선택지는 서로 구분되고 실제로 실행 가능해야 한다. 권장안이 있으면 근거와 함께 표시하되 답변란을 대신 체크하지 않는다. 대화로 받은 명시적 답변도 원문 취지와 함께 파일에 반영할 수 있다. 무응답을 승인으로 간주하지 않는다. 질문 파일 생성 시 사람에게 위치와 필요한 결정을 알리고, 관련 없는 작업은 계속한다.

## 6. 초기 DB 설계와 공통 백엔드

### 6.1 DB 설계 선행 게이트

DB 스키마 전문가를 개발 초기에 배정한다. **도메인 모델·마이그레이션 구현은 초기 스키마 검토를 통과한 후 시작한다.** 공통 문서를 준비하는 동안 다른 에이전트는 요구사항 분석, 시안 동선 설계, 수용 기준 및 AI 연결 검증 계획 등 문서 작업을 병렬 수행한다. 실제 AI 연결 검증은 공통 문서 준비 완료 후 구현 초기에 수행한다.

DB 설계 산출물에는 다음을 포함한다.

- `01`의 엔티티와 도메인 소유권, PK/FK, null 허용, 고유·체크 제약, 인덱스, 관계별 삭제/비활성화 정책.
- 계정·역할·지역·매장 매핑, 4단계 가이드라인·버전·Reference, 제출·입력 스냅샷·리뷰·재제출 연결.
- 분석 작업과 처리 시도의 분리, 동시 점유·재처리 중복 방지, 종료 후 늦게 도착한 결과 처리.
- 이슈·후속 조치, 알림 수신자·읽음 상태, 플랫폼 운영 변경 이력과 필요한 Mock 분석 데이터.
- 대시보드 지표 정의와 집계 근거. 원본 업무 데이터와 집계 값을 중복된 진실의 원천으로 만들지 않는다.
- 마이그레이션 의존 순서, 초기 시드 순서, 권한·과거 기록 보존·동시성 검증 시나리오.

오케스트레이터와 관련 도메인 담당자가 `00`·`01` 정합성을 검토하고 설계 결과를 후속 DB 문서에 확정한다. 이후에도 변경은 가능하지만 DB 전문가가 마이그레이션 충돌과 기존 데이터 영향을 조정한다.

각 모듈은 SQLAlchemy 모델·Pydantic 스키마·서비스·APIRouter·권한 dependency·테스트를 책임별로 나눈다. DB 마이그레이션은 Alembic으로 관리한다. 동일한 서비스 함수와 권한 정책을 업무 API·작업자에서 재사용한다. 도메인별 마이크로서비스나 시안 전용 서버를 추가하지 않는다.

알림은 이번 요청의 도메인 분리를 반영하되 `00`의 범위 제한을 유지한다. MVP에서는 저장된 앱 내부 알림을 조회·읽음 처리하는 수준으로 구현하며, 실시간 전송·OFC 자동 외부 통지·이메일·SMS·푸시 인프라는 추가하지 않는다.

## 7. 모듈별 TDD와 필수 로컬 AI 서버

### 7.1 TDD 실행 순서

모든 구현 모듈은 아래 순서로 진행한다. 백엔드·AI 서버·프론트의 검증 가능한 동작과 시드 로직에 적용한다.

1. **RED**: 수용 기준을 테스트로 작성하고 실제 실행하여 원하는 이유로 실패하는지 확인한다. 환경 오류만 발생한 것을 요구사항의 실패 증거로 사용하지 않는다.
2. **GREEN**: 해당 테스트를 통과시키는 최소 구현을 작성한다.
3. **REFACTOR**: 책임·중복·명명을 정리하고 관련 테스트를 다시 실행한다.
4. **INTEGRATE**: 계약·권한·DB·다른 모듈과 연결되는 동작을 검증하고 결과를 기록한다.

정상 흐름뿐 아니라 역할별 조회 범위, 비활성 계정, 유효하지 않은 입력, 빈 데이터, 중복 요청, 실패 복구 등 담당 모듈의 실제 위험을 검증한다. 구현 세부사항을 그대로 복제한 테스트나 무의미한 테스트 개수 늘리기를 피한다. 발견한 결함은 재현 테스트를 먼저 추가한 뒤 수정한다.

도메인·DB는 pytest + FastAPI TestClient/HTTPX, React 동작은 Vitest/Testing Library, 브라우저 통합은 Playwright를 기본으로 사용한다. 동시 작업 점유·재처리·제약 검증은 PostgreSQL에서 수행한다. 이미지·문서처럼 코드가 아닌 산출물에는 TDD를 형식적으로 적용하지 않고 사전 체크리스트와 실제 산출물 검수로 검증한다.

### 7.2 로컬 AI 완료 조건

- `ai-service`에 Python 로컬 서버를 반드시 구현한다. 공통 백엔드의 독립 Python 작업자만 내부 호출하며 브라우저는 직접 연결하지 않는다.
- 제출 사진, 질문, 적용 가이드라인, Reference **실제 이미지**를 입력받아 Codex 실행 어댑터로 분석하고 구조화 JSON을 검증한다.
- `01`의 로컬 서버는 로컬 API·실행 프로세스를 뜻한다. 모델 추론까지 오프라인이라는 의미로 설명하지 않는다.
- 단위 테스트에서는 실행기를 대체할 수 있지만 최종 인수검증에는 실제 분석 성공 증거가 필요하다. CLI 실행·인증·연결 실패를 고정 샘플 답변으로 숨기지 않는다.
- 잘못된 이미지, 잘못된 JSON, 타임아웃, 실패한 작업의 수동 재처리, 중복/늦은 결과를 검증한다.
- 사진 속 문자·사용자 질문은 분석 데이터로 취급한다. 저장소 작업 지시를 모델 컨텍스트로 섞거나 인증 값을 결과·로그에 노출하지 않는다.

## 8. 5개 프론트엔드 컨셉과 독립 검증

### 8.1 시안의 차별화 기준

다음은 시작용 컨셉이다. 에이전트는 기능·권한을 유지하는 범위에서 세부 디자인을 발전시키고 결정 근거를 기록한다.

| 시안 | 중심 경험 | 구별되어야 할 요소 |
|---|---|---|
| `concept-01` | 관제 현황 중심 | 밀도 있는 지표·테이블, 필터, 요약에서 상세로 이동 |
| `concept-02` | 오늘의 업무 중심 | 할 일·확인 필요 건의 우선순위, 처리 흐름과 진행 상태 |
| `concept-03` | 사진과 근거 중심 | Reference·제출 사진 비교, 평가 근거와 개선 이력 배치 |
| `concept-04` | 현장 사용 중심 | 모바일 동선, 큰 조작 영역, 단계별 제출·처리 안내 |
| `concept-05` | 탐색과 비교 중심 | 지역·매장·카테고리 탐색, 비교·추이와 데이터 관리 연결 |

각 시안은 점주·영업 관리자·플랫폼 운영자 기능을 모두 제공한다. 프론트 개발 에이전트는 API 준비 전 계약 기반 Mock으로 진행할 수 있으나, 완료 판정 전에는 공통 백엔드에 연결해야 한다. Mock 사용 상태를 숨기지 않는다.

### 8.2 통합 테스트 에이전트

프론트 작성자와 다른 서브에이전트가 **5개 시안 각각**을 검증한다. 가용 슬롯이 적으면 동일 테스트 담당자가 여러 시안을 순서대로 검증할 수 있지만, 시안별 체크리스트와 보고서는 분리한다.

공통 기능 테스트를 재사용하되 각 시안의 실제 버튼·입력·페이지 이동을 수행한다. 하나의 시안 통과로 나머지를 통과 처리하거나 API 테스트만으로 UI 통합을 대체하지 않는다.

필수 검증 범위:

- 5개 역할 로그인, 역할별 메뉴·직접 URL·API 접근 제한, 담당 외 매장 차단.
- 계정 비활성화 및 역할·매장 연결 변경이 기존 로그인 요청에도 반영되는지 확인.
- 기준·Reference 등록 → 점주 사진·질문 제출 → 실제 AI 분석 → 결과·이력 → 관리자 대시보드·근거 조회.
- 재제출·전후 비교, OFC 확인 필요 이슈 및 조치 상태, 알림 수신자·읽음 상태의 분리.
- 플랫폼 운영자의 상태 조회·실패 재처리와 업무 사진·평가 본문 접근 제한.
- 로딩·빈 데이터·입력 오류·분석 실패·판단 불가 상태, Mock/생성 이미지 표시.
- 주요 화면의 데스크톱·모바일 배치, 키보드 조작, 오류 안내 및 각 컨셉 패키지의 단일 빌드.

각 시안에서 최소 한 번은 실제 로컬 AI 서버까지 이어지는 제출 흐름을 검증한다. 모델 응답은 문장 완전 일치 대신 입력 연결, 구조 유효성, 근거 참조, 저장·화면 표시를 확인한다. AI 동시 실행 제한을 지키며 실제 분석 테스트는 대기열로 조정한다.

### 8.3 테스트 격리와 보고

- 통합 테스트는 별도 테스트 DB와 미디어 경로를 사용하고 브라우저 세션을 격리한다. 백엔드 소스는 동일하게 사용한다.
- 병렬 테스트 데이터는 고유 식별자로 분리한다. 동일 데이터를 수정하는 시나리오와 DB 초기화는 직렬화한다. 다른 에이전트의 진행 중인 테스트나 시연 데이터를 초기화하지 않는다.
- 보고서는 검증한 소스 상태, 시안, 역할, 데이터 버전, 실행 명령, 기대·실제 결과, 스크린샷/trace 위치, 결함과 재검증 결과를 포함한다.
- 결과는 `PASS / FAIL / BLOCKED / NOT_RUN`으로 구분한다. 환경·인증 문제로 실행하지 못한 테스트는 통과가 아니다.
- 공통 백엔드·공유 코드 결함은 소유자에게 수정 요청하고 영향을 받는 모든 시안에서 회귀 검증한다.

### 8.4 시안별 기획·디자인 에이전트와 명세 관리

각 프론트 시안마다 전담 기획·디자인 에이전트를 배정한다. `design-concept-01`은 `web-concepts-01`, 나머지도 같은 번호의 프론트를 담당한다. 이 에이전트의 목표는 **개발자가 임의로 디자인을 추측하지 않고 구현할 수 있고, 독립 검수자가 실제 화면과 대조할 수 있는 기획·디자인 기준을 완성하는 것**이다. 컨셉별 담당은 분리하고 가용 슬롯에 따라 병렬 또는 순차 실행한다.

기획·디자인 담당은 00·01·02와 공통 기능·API 계약 안에서 정보 구조, 디자인 방향, 표현 방식을 스스로 결정한다. §8.1의 시작용 컨셉을 구체화하고 다른 시안과 구분되는 근거를 남긴다. 기획을 이유로 필수 기능·역할·권한을 변경하지 않는다. 최종 시안 선택은 사람의 몫이며 시안별 디자인 정의에 별도 사람의 승인을 일괄 요구하지 않는다.

#### 저장 위치와 필수 산출물

```text
execute/
├─ design/concept-0N/
│  ├─ brief.md                 # 목표 사용자·업무·정보 구조·컨셉
│  ├─ design-spec.md           # 룩앤필·톤앤매너·토큰·컴포넌트·화면 명세
│  ├─ acceptance.md            # 식별자별 검수 기준과 화면·상태 적용 범위
│  └─ references/              # 와이어프레임·참고 이미지·출처 등 필요 자료
├─ designReview/concept-0N/
│  ├─ review-001.md            # 검수 대상 버전·항목별 결과·불일치·재검수
│  └─ evidence/               # 실제 실행 화면 캡처 및 비교 증거
├─ checkList/design-concept-0N/{task-id}.md
├─ checkList/design-review-concept-0N/{task-id}.md
├─ workHitory/design-concept-0N/{task-id}.md
└─ workHitory/design-review-concept-0N/{task-id}.md
```

`0N`은 `01`부터 `05`까지다. 질문은 기존 `execute/question/{module-id}` 규칙을 그대로 따른다. 디자인 원본 명세는 `execute/design`에 두고 docs 및 작업 이력에서는 링크하여 서로 다른 정본을 만들지 않는다. 위 구조는 구현 단계에 생성할 대상이며 현재 문서 수정 요청만으로 생성하지 않는다.

| 문서 | 반드시 정의할 내용 |
|---|---|
| brief.md | 대상 역할과 핵심 과업, 화면 목록·탐색 구조·주요 동선, 컨셉의 목적과 차별점, 다른 시안과의 차이 |
| design-spec.md | 룩앤필, 색상과 의미, 타이포그래피, 간격·그리드·밀도, 모서리·그림자·아이콘·사진·차트 표현, 공통 컴포넌트 상태 |
| design-spec.md | 톤앤매너와 실제 문구 예시: 안내·행동 버튼·성공·오류·AI 판단 불가·Mock 배지, 현업 용어와 표현 일관성 |
| design-spec.md | 점주·OFC·지역·본사·플랫폼 운영자의 화면별 배치·강조 정보, 데스크톱/모바일 레이아웃과 전환 기준, 로딩·빈 상태·오류·긴 텍스트·대량 목록의 표현 |
| acceptance.md | 화면·상태별 기준 ID, 연결된 명세 절, 확인 방법, 기대 결과, 필수/권장 구분, 반응형·키보드·초점·가독성 기준 |

색·크기·간격은 가능한 한 토큰명과 구체 값으로 명시한다. “세련되게”, “깔끔하게” 같은 추상 표현만으로 완료하지 않는다. 대표 화면은 와이어프레임 또는 구체적인 영역·컴포넌트 배치 설명을 제공한다. 참고 자료에는 출처와 차용할 요소를 남기며, 참고 이미지 자체를 구현 완료 증거로 사용하지 않는다.

#### 개발 인계와 변경

1. 기획·디자인 에이전트는 작업 전 체크리스트를 작성하고 명세 버전과 검수 기준 ID를 부여한다.
2. 공통 문서 준비와 병렬로 디자인 명세를 작성한다. 해당 프론트 화면 구현 전에는 기본 컨셉·토큰·공통 컴포넌트·대상 화면 기준이 준비되어야 한다. 다른 시안의 세부 디자인을 기다리느라 준비된 시안이나 백엔드 작업을 멈추지 않는다.
3. 프론트 개발 담당은 명세를 읽고 적용할 버전을 체크리스트에 기록한다. 공통 계약 완료 후 해당 디자인 기준에 따라 구현하며 명세의 누락·충돌은 기획·디자인 담당에게 전달한다.
4. `execute/design`의 MD도 §2.1의 후속 MD 변경 전파 대상이다. 수정 시 프론트 개발·디자인 검수·통합 테스트·매뉴얼 담당 및 오케스트레이터에게 변경과 영향을 알리고 확인·반영을 추적한다.
5. 구현 편의나 검수 실패를 숨기기 위해 기준을 사후 완화하지 않는다. 합리적인 디자인 변경은 이유·전후·영향을 남기고 기준을 갱신한 뒤 해당 화면을 다시 검수한다.

### 8.5 독립 에이전트의 최종 디자인 검수

각 시안은 **해당 시안의 기획·디자인 및 프론트 구현을 맡지 않은 별도 디자인 검수 에이전트**가 최종 검수한다. 기능 통합 테스트의 통과로 디자인 검수를 대체하지 않는다. 검수 담당은 기능 테스트 담당과도 역할을 분리하여 배정하며, 가용 슬롯이 적으면 순차 실행할 수 있다. 한 검수 에이전트가 여러 시안을 검수하더라도 시안별 결과는 분리한다.

검수의 목표는 취향에 따른 순위 선정이 아니라 **기획·디자인 명세가 실제 실행 화면에 반영됐는지 증거로 확인하는 것**이다.

1. 최신 디자인 명세·검수 기준과 변경 전파 이력을 확인하고, 검수 대상 소스/빌드 버전·명세 버전·시연 데이터·브라우저·viewport를 기록한다.
2. 실제 빌드된 프론트를 브라우저에서 열어 각 역할의 주요 화면과 동선을 확인한다. 소스·CSS 값·DOM 존재 여부만 확인하거나 개발 담당자의 보고만 읽고 통과 처리하지 않는다.
3. 컨셉·정보 우선순위·레이아웃·룩앤필·톤앤매너·토큰·컴포넌트 일관성과 데스크톱/모바일 표시를 대조한다. 로딩·빈 상태·오류·판단 불가, 긴 데이터·이미지 비율·표/차트 밀도, 초점 표시·키보드 접근·가독성도 해당 기준에 따라 확인한다.
4. 실제 화면 캡처를 evidence에 저장하고 기준 ID별 `PASS / FAIL / BLOCKED / NOT_RUN` 결과를 기록한다. 불일치에는 명세상 기대와 실제 화면, 영향, 위치, 수정 담당자, 증거 링크를 포함한다.
5. 발견한 불일치를 프론트 개발 담당과 기획·디자인 담당 및 오케스트레이터에게 전달한다. 개발 담당이 수정하면 검수 담당이 같은 기준으로 재검수하고 결과를 추가한다. 수정했다는 회신만으로 PASS로 바꾸지 않는다.
6. 필수 디자인 기준의 FAIL/BLOCKED/NOT_RUN이 남아 있으면 해당 시안의 디자인 완료를 선언하지 않는다. 권장 개선 항목은 남은 영향과 처리 결정을 기록한다. 최종 수정 후 영향받는 기능 테스트와 매뉴얼 캡처도 갱신한다.

검수 보고서는 다음 표를 포함한다.

| 기준 ID / 명세 절 | 역할·화면·상태·viewport | 기대 / 실제 | 결과 | 증거 링크 | 수정 담당·재검수 결과 |
|---|---|---|---|---|---|
| {criterion-id} | {검수 범위} | {명세 대비 관찰} | NOT_RUN | {캡처} | {후속 조치} |

오케스트레이터는 5개 시안 각각에 대해 기능 통합 테스트와 최종 디자인 검수가 모두 충족됐는지 확인한다. 디자인 검수 결과는 사람이 최종 컨셉을 선택할 때 제공할 비교 자료에 포함하지만, 검수 에이전트가 최종 컨셉을 선택하거나 다른 시안을 폐기하지 않는다.

## 9. 현실적인 시연 데이터와 매대 이미지

### 9.1 데이터 에이전트

개발 중에는 최소 시드로 연결을 돕고, 기능 개발 완료 후에는 최종 스키마에 맞는 전체 시연 데이터를 실제 적재한다. 파일만 만들어 두고 적재 완료로 보고하지 않는다.

| 데이터 | 구성 기준 |
|---|---|
| 지역·매장 | 가상 지역과 5~10개 매장, 서로 다른 상권·담당 관계·제출 현황 |
| 사용자·권한 | 5개 역할별 1~2개 계정, 담당 범위 차이, 비활성·연결 누락 사례 |
| 기준·Reference | 본사·지역·매장·매대 4단계 기준과 버전, 카테고리별 Reference 2~3장 |
| 카테고리 | 구조는 4~6개 이상 등록 가능, 초기 실제 분석 시연은 `01`에 따라 1~2종부터 검증 |
| 제출·평가 | 매장당 과거 제출·리뷰 3~5건, 개선 전후·확인 필요·미제출·판단 불가의 구분 |
| 이슈·알림 | 담당자·제출·리뷰에 연결된 미해결/해결 이슈, 역할에 맞는 읽음/안 읽음 사례 |
| 매출·재고 | 지원 기능에 필요한 가상 SKU·수량, 최근 4~8주 데이터, Mock 표시 |
| 플랫폼 운영 | 실패 작업·재처리·권한 변경·비활성화 및 실제 관계에 맞는 변경 이력 |

실제 인물·실제 가맹점의 정보로 오인되지 않게 가상 명칭을 사용한다. 과거 리뷰 샘플과 실제 모델이 새로 생성한 결과를 구분하고, 장애 fixture를 실제 서비스 장애로 표시하지 않는다. 점수·사진·기준·이슈·알림의 연결과 시간 순서가 일관되어야 한다.

시드는 안정적인 식별자와 재현 가능한 값으로 구성하여 재실행 시 중복되지 않도록 한다. 기본 실행으로 기존 사용자 데이터를 삭제하지 않는다. 명시적인 개발용 초기화는 대상 DB·경로를 확인한 경우에만 수행한다. 적재 후 개수·관계·권한·이미지 존재 여부와 주요 시연 동선을 검증한다.

### 9.2 이미지 생성 에이전트

구현 단계에서 이미지 생성 담당 서브에이전트를 두고 사용 가능한 이미지 생성 도구로 **실제 매대 이미지 파일**을 만든다. 도구를 사용할 수 없으면 제약과 영향을 기록하고 사람에게 필요한 선택을 질문한다. 빈 파일·외부 이미지 링크·생성 프롬프트만으로 완료 처리하지 않는다.

이미지 세트에는 다음 용도를 포함한다.

1. 우수 매대 Reference: 카테고리와 기준을 시각적으로 설명하는 정돈된 매대.
2. 점주 분석 요청: 진열 간격, 페이싱, 분류 혼재 등 관찰 가능한 개선 지점이 있는 사진.
3. 개선 전후: 같은 매대 구도에서 지정한 문제를 개선한 비교 사진.
4. 판단 곤란: 저조도·가림·흔들림 등 재촬영/OFC 확인 흐름을 보여주는 사진.

`manifest`에는 파일 경로, 이미지 ID, 카테고리, 용도, 생성 프롬프트, 연결할 기준·Reference·제출, 관찰 가능한 특징, 검수 상태를 기록한다. 이미지가 실제로 설명과 맞는지 시각적으로 확인하고 잘못된 이미지는 다시 생성하거나 연결을 수정한다.

Reference와 평가용 제출에 같은 이미지를 재사용하여 비교 성공을 꾸미지 않는다. 생성 의도만으로 정답·점수·모델 정확도를 확정하지 않는다. Golden Case는 별도 기대 관찰 사실을 검수한 뒤 사용한다. 생성 이미지는 UI와 매뉴얼에서 `AI 생성 시연 이미지`, 가상 수치는 `Mock 데이터`로 구분한다.

데이터 담당자는 이미지 파일을 실제 보호된 미디어와 Reference/제출 데이터에 연결하고, 테스트 담당자는 등록·열람·분석·이력까지 검증한다.

## 10. 시안별 HTML User Manual

각 시안의 기능이 완성되면 매뉴얼 담당 에이전트를 배정하여 `deliverables/manuals/concept-0N/index.html`을 작성한다. 5개 시안에 맞는 **5개 HTML 매뉴얼**을 제공한다.

필수 내용:

- 시안명, 컨셉, 역할별 화면 시작 위치 및 실제 실행 구성.
- 점주의 매장 선택·사진/질문 제출·상태·결과·재제출·이력 확인.
- OFC·지역·본사의 데이터 관리·관제·근거 확인·이슈 대응·분석.
- 플랫폼 운영자의 계정·범위·기준 정보 관리·실패 재처리·운영 이력.
- 각 시안의 실제 화면 캡처, 메뉴·버튼명, 단계별 행동과 기대 결과.
- Mock/AI 생성 이미지 설명, 권한 제한, 오류·판단 불가 시 행동, 알려진 제약.
- 준비된 데이터로 실행할 수 있는 처음부터 끝까지의 시연 순서.

HTML은 UTF-8로 작성하고 목차·내부 링크·읽기 쉬운 화면 구성을 제공한다. 설명과 캡처용 파일은 상대 경로로 함께 제공하여 외부 CDN 없이 열람할 수 있게 한다. 실제 서비스 연결이 필요한 기능은 실행 조건을 안내한다. 인증 비밀 값은 포함하지 않는다.

매뉴얼 담당자는 실제 완성된 시안을 확인하여 작성하고, 테스트 담당자는 링크·이미지·안내 동선을 검수한다. 기능 QA 또는 디자인 검수 수정으로 화면이 바뀌면 매뉴얼도 갱신하고 최종 캡처를 검수 통과 화면과 맞춘다. 다른 시안의 캡처나 미구현 기능을 완성 기능처럼 안내하지 않는다.

## 11. 오케스트레이터 실행 순서와 완료 게이트

| 단계 | 실행할 작업 | 다음 단계 진입 조건 |
|---|---|---|
| G0 준비 | 작업 시작 지시 수신, 강제·기존 문서 조사, 체크리스트·문서 작업 배정표 작성 | 필요한 공통·서비스 문서와 담당자·선행 관계 확정 |
| G1 공통 문서 | §5.0의 공통 문서 작성·상호 검토, 시안별 기획·디자인 에이전트 배정 및 명세 작성 | 공통 문서 완료 조건 충족 → 추가 승인 없이 G2 자동 시작 |
| G2 병렬 구현 | 서비스별 세부 문서와 시안별 디자인 기준 준비 후 TDD, 로컬 AI 연결 조기 검증·작업자, 5개 시안, 최소 시드 | 각 모듈 자체 검증 및 실제 API 연결 |
| G3 시연 구성 | 전체 시드·생성 이미지 적재, 단계별 업무 연결 | 시연 데이터 정합성, 실제 분석 및 권한 검증 |
| G4 독립 검증 | 시안별 통합 테스트와 독립 최종 디자인 검수, 수정·재검수, 매뉴얼 작성 | 5개 시안의 기능·필수 디자인 기준 통과, 최종 데이터 기준 회귀 검증 |
| G5 인계 | 5개 매뉴얼 검수, 실행표·비교 자료·제약 정리 | 사람이 실행·비교·선택할 수 있는 결과물 완비 |

G0 → G1 → G2는 오케스트레이터가 조건 충족 여부를 판단하여 자동 전환한다. G1의 공통 문서 완료 전에는 서비스 소스 구현을 시작하지 않는다. 이후 독립 작업은 단계 일부를 겹쳐 진행할 수 있다. 예를 들어 첫 시안 완성 후 나머지 개발 중에도 해당 시안 통합 테스트와 매뉴얼을 시작한다. 단, 선행 스키마 검토나 최종 실제 AI 검증을 생략하는 근거로 병렬 처리를 사용하지 않는다.

- [ ] 모든 시안이 공통 기능·권한을 제공하고 공통 백엔드와 연결된다.
- [ ] 독립 서브에이전트가 5개 시안 각각을 검증하고 결과·결함·재검증을 남겼다.
- [ ] 현실적인 가상 데이터와 실제 생성 이미지가 적재되어 시연 흐름이 연결된다.
- [ ] 5개 HTML 매뉴얼이 실제 화면·기능과 일치하고 정상 열람된다.
- [ ] 작업별 체크리스트·이력·필요한 질문과 후속 문서 변경 내역이 남아 있다.
- [ ] 후속 MD 변경이 영향 대상 에이전트 모두에게 전파되고 반영·검증 또는 영향 없음 확인이 기록되어 있다.
- [ ] 필수 테스트의 FAIL/BLOCKED/NOT_RUN이 완료로 포장되지 않았다.
- [ ] 사람이 비교할 실행 위치, 매뉴얼, 컨셉별 특징, 검증 상태, 알려진 제약이 정리되어 있다.

### 사람의 최종 컨셉 선택

5개 결과물 준비 후 `execute/question/frontend-selection/select-concept.md`에 `concept-01`부터 `concept-05`까지의 객관식 선택지와 실행·화면·매뉴얼 링크를 제공한다. 에이전트는 비교 의견을 제시할 수 있지만 최종 선택을 대신하지 않는다.

사람의 선택 전에는 모든 시안 소스를 보존한다. **기술 구현·검증 완료**와 **최종 컨셉 선택 대기**를 별도로 보고한다. 선택 이후 대표 실행 구성을 지정하는 작업은 결정 내용을 기록하고 진행하며, 선택되지 않은 시안의 삭제·대규모 병합은 선택만으로 자동 수행하지 않는다.
