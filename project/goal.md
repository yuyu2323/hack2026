/goal 본사·지역·OFC가 매장별 확인 필요 사항을 사진과 운영 기준에 근거해 파악하고, 점주가 AI 피드백을 받아 조치한 뒤 새 사진으로 개선 결과를 확인할 수 있는 StoreLoop를 구현·검증하여 시연 가능한 상태로 완성하라.

작업 대상은 yuyu2323/hack2026 저장소의 project 디렉터리다. 실제 저장소와 작업 경로를 확인한 뒤 docs/00-vision.md → docs/01-architecture.md → docs/02-development-orchestration.md 순서로 읽고 실행 기준으로 삼아라. 아래 경로는 project 기준이다. 이 목표가 실제 실행되면 필요한 후속 문서 작성부터 구현·검증·인계까지 이어서 수행하라.

1. 해결할 문제와 사용자

점주는 진열 기준과 개선 방법을 확인하기 위해 OFC의 응답을 기다리고, 본사·지역·OFC는 분산된 사진·기준·문의·조치 기록 때문에 여러 매장의 지원 우선순위와 개선 결과를 파악하기 어렵다. 플랫폼 운영자는 계정·담당 연결과 분석 장애를 관리해야 한다. 운영 데이터 관리 → 사진 기반 평가 → 관제 → 검토·조치 → 새 사진 재제출·결과 확인을 연결하여 이 문제를 해결하라.

2. 완료 상태

- 점주가 담당 매장을 선택하고 사진·질문을 제출하여, 적용 가이드라인·Reference와 연결된 실제 AI 결과의 위치·근거·개선 행동·판단 한계를 확인할 수 있다. 조치 후 새 사진을 이전 제출에 연결하고 전후 결과와 이력을 조회할 수 있다.
- OFC·지역·본사가 권한 범위에서 매장·기준·Reference·이력을 관리하고, 대시보드에서 확인 필요 건을 찾아 원본 근거 확인·이슈 대응·후속 확인까지 수행할 수 있다. 앱 내부 알림, 기본 기간 집계와 Mock 매출 상관분석을 제공한다.
- 플랫폼 운영자가 영업 사진·질문·평가·매출 본문에 접근하지 않고 계정·역할·담당 연결·기준 정보·서비스 상태를 관리하며, 실패 작업 재처리와 운영 이력을 확인할 수 있다.
- 공통 FastAPI 백엔드·PostgreSQL·독립 분석 작업자·실제 Codex 분석을 수행하는 별도 Python AI 서버를 연결한다. React·TypeScript 기반의 관제 중심, 업무 중심, 사진 근거 중심, 모바일 현장 중심, 탐색·비교 중심 시안 5개를 각각 완성한다. 각 시안은 모든 역할과 동일한 필수 기능을 포함하고 독립적으로 빌드·실행할 수 있어야 한다.
- 가상 매장 5~10개와 5개 역할, 초기 분석 카테고리 1~2종, Reference·개선 전후·판단 곤란 이미지와 연결된 시연 데이터를 준비한다. 시안별 HTML 매뉴얼 5개, 실행 안내, 비교 자료와 검증 증거를 제공하여 사용자가 직접 실행하고 최종 시안을 선택할 수 있게 한다.

3. 완료 확인 기준

- 5개 시안 각각에서 실제 브라우저로 5개 역할의 핵심 흐름과 데스크톱·모바일 화면을 확인한다. 각 시안에서 최소 한 건은 사진·질문·기준·Reference → 실제 로컬 AI 분석 → 결과 저장 → 화면 재조회까지 실행한다.
- 담당 밖 매장과 원본 이미지 접근 차단, 기존 세션의 계정 비활성화·역할·담당 변경 반영, 플랫폼 운영자의 영업 본문 접근 차단을 테스트한다.
- 잘못된 이미지, 빈 데이터, 판단 불가, 모델 실패·시간 초과·잘못된 결과, 재처리 중복, 작업자 중단·늦은 응답을 검증한다. 동시 점유·재처리 검사는 PostgreSQL에서 수행하고 재시작 후 원본·기준 버전·시도·결과·이력 보존을 확인한다.
- 대시보드 수치와 상세 목록이 같은 권한·기간 조건에서 일치해야 한다. 새 사진 재제출과 같은 입력의 장애 재처리를 구분하고, Mock 상관계수는 독립 계산과 대조하며 표본 부족·결측·분산 0을 처리한다.
- 각 시안의 빌드·독립 기능 통합 검증·독립 디자인 검수가 통과하고, 매뉴얼의 링크·이미지·실제 화면 안내가 일치해야 한다. 단위 테스트의 모의 응답과 실제 모델 분석 증거를 구분한다.
- 기준별 기대 결과·실제 결과·소스 버전·명령·화면 증거를 기록한다. 모델 응답 시간은 실제 측정하며, 30초 응답과 50% 현장 개선 목표의 달성을 측정 없이 주장하지 않는다.

4. 제약

- 00·01·02의 제품 범위·기술 구성·권한 경계를 유지한다. 이전 리허설은 참고 자료로 읽고 코드·DB·설정·프로세스를 변경하지 않는다. 기존 원본·실패 시도·사용자 데이터를 보존한다.
- 실제 POS·매출·재고 연동, 카메라·로봇 제어, 오프라인 모델 추론, 외부 업무 알림 인프라는 이번 범위에서 제외한다. 공개 배포와 행사 제출은 별도 허용된 범위에서 수행하고 구현 완료와 구분한다.
- 생성 이미지는 AI 생성 시연 이미지, 가상 데이터는 Mock으로 표시한다. 사진만으로 품절·실재고·현장 개선 효과를 단정하지 않고, 모델 호출 실패를 샘플 성공으로 대체하지 않는다.
- 실제 키·토큰·비밀번호·인증 자료를 소스·문서·매뉴얼·공유 로그·커밋에 넣지 않는다. 02의 Git 검사·커밋·원격 작업 정책을 적용한다. 승인 우회와 무제한 모델 재호출은 하지 않는다.

5. 판단 범위

- 에이전트는 후속 명세, DB·API 세부 설계, 시안별 디자인, 의존성 선택, 테스트, 구현·리팩터링·결함 수정, 시드·이미지·매뉴얼 작성과 작업 순서를 자율 결정한다. 현재 제공된 도구·인증으로 필요한 실제 분석과 이미지 생성을 수행한다. 이미 허용된 작업과 단계 전환을 반복 승인받지 않는다.
- 오케스트레이터는 독립 서브에이전트에게 사용자 결과·수정 파일·입력 계약·검증 방법·반환 증거를 지정한다. DB·공유 파일은 단일 수정 담당을 두고, 구현자와 독립된 기능 검증·디자인 검수 담당을 배정한다. 가용 슬롯에 맞춰 순차·병렬 배치하고 반환 결과를 실제 통합 상태로 인수한다.
- 강제 문서의 변경·실제 충돌, 제품 범위 변경, 새로운 유료 결제, 허용되지 않은 외부 공개·원격 반영·운영 환경 변경·최종 제출은 필요한 결과물을 준비한 뒤 사용자 판단을 요청한다. 기존에 받은 권한은 유지하고 질문과 관계없는 작업은 계속한다. 최종 시안 선택은 사용자가 한다.

6. 검증과 종료

실행 직후 이 /goal 원문, 시작 시각, 기준 문서 버전·해시와 실제 세션 로그 위치를 보존하라. 이후 문서나 목표가 바뀌면 이전본·변경 이유·시각·사용자 지시·영향·재검증 결과를 남기고 관련 담당자에게 전파하라. 과거 리허설의 성과를 이번 실행 결과로 계산하지 마라.

각 작업은 execute/checkList에 수용 기준을 먼저 작성하고, execute/workHitory에 수행·실패·결정·검증 증거를 기록하라. 필요한 사용자 결정은 execute/question에 남겨라. 공통 문서와 초기 DB 설계를 검토한 뒤 추가 시작 승인을 기다리지 않고 구현하라. 기능은 실패하는 테스트 → 구현 → 통과 → 필요한 정리·회귀 → 실제 통합 순서로 진행하고, 발견된 결함은 재현·수정·같은 조건의 재검증으로 닫아라. 이미지·디자인·매뉴얼은 실제 산출물로 검수하라.

필수 기능을 우선 연결하고 02가 정한 후속 개선·독립 검증까지 수행하라. 5개 시안·공통 서비스·시연 데이터·매뉴얼의 필수 기준이 모두 통과하고 사용자가 재실행·비교할 수 있을 때 기술 구현 목표를 완료하라. 최종 인계에는 실행 위치·명령·검증표·결과물·남은 한계·서비스 실행 상태·실제 로그 연결과 시안 선택지를 포함하라. 최종 시안 선택 대기는 기술 구현 완료와 별도로 표시하라.

FAIL·BLOCKED·NOT_RUN이 남은 필수 항목을 완료로 표시하거나 통과 기준을 낮추지 마라. 권한·환경·사용량 때문에 진행할 수 없는 항목은 원인과 재개 조건을 남기고 가능한 독립 작업을 마쳐라. 사용자의 중지 지시나 실행 한도에 도달하면 미완료 상태를 정직하게 인계하라. 완료 후에는 범위 밖 확장이나 불필요한 반복 실행을 이어가지 마라.
